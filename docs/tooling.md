# Development Tooling

This document covers the tools used to develop and maintain this
project: linting, formatting, type checking, commit conventions, and
the automation (pre-commit hooks and CI) that ties them together. See
[testing.md](testing.md) for the test suite itself, and
[data-tables.md](data-tables.md) for the data/schema architecture.

## Tool overview

| Tool                | Purpose                                          |
|---------------------|--------------------------------------------------|
| git-cliff           | Changelog generation from commit history         |
| gitlint             | Commit message validation                        |
| mypy                | Static type checking                             |
| pre-commit          | Runs the above automatically at commit/push time |
| pymarkdownlnt       | Markdown linting and formatting                  |
| pytest / pytest-cov | Test suite and coverage enforcement              |
| ruff                | Python linting and formatting                    |
| yamllint            | YAML linting (default settings)                  |

`pyproject.toml` is the primary configuration file for this project,
covering packaging, ruff, mypy, and pytest settings. A few tools don't
support `pyproject.toml` and use their own dedicated config files
instead — this is a deliberate, documented exception rather than an
inconsistency:

- `.yamllint.yaml` — yamllint has no `pyproject.toml` support
- `.gitlint` — gitlint has no `pyproject.toml` support

## Pre-commit hooks

Hooks run automatically at three different points in the git
workflow, each requiring its own one-time installation:

```bash
pre-commit install -t pre-commit -t pre-push -t commit-msg
```

- **pre-commit stage** — runs on every `git commit`. Covers file
  hygiene (trailing whitespace, EOF newlines, JSON/TOML validity,
  merge conflict markers), plus linting/formatting via ruff,
  yamllint, and pymarkdown.
- **commit-msg stage** — runs after you write a commit message, via
  gitlint. Validates message length and Conventional Commits format
  before the commit is created.
- **pre-push stage** — runs on `git push`. Runs the full pytest suite,
  scoped to changes under `src/`, `tests/`, `schemas/`, and
  `pyproject.toml`.

## Coverage configuration

Coverage is measured via `pytest-cov`, configured in
`[tool.pytest.ini_options]` (the `--cov-*` flags) and
`[tool.coverage.run]` (exclusions). The auto-generated `_version.py`
is excluded from coverage measurement via `omit`, since it's
generated at build time by `setuptools_scm` rather than handwritten
— testing it would mean asserting a string equals itself.

## Linting conventions enforced

Beyond general style, a few `ruff` rule categories enforce specific
conventions worth knowing when writing new code:

- **`PT006`** — `@pytest.mark.parametrize` with multiple parameter
  names uses a tuple (`("a", "b")`), not a comma-separated string
  (`"a, b"`). Single-name cases stay a plain string.
- **`PT018`** — compound assertions (`assert x and y`) are split into
  separate `assert` statements, so a failure reports which condition
  actually failed rather than both.
- **`ANN401`** — `Any` in argument types is generally disallowed, with
  a targeted exception for `tests/helpers.py`, which deals with raw,
  untyped YAML data by nature.
- **`PTH`** — use `pathlib.Path` rather than `os.path`, per this
  project's cross-platform requirement.
- **`pydocstyle` (Google convention)** — docstrings follow Google
  style (no type annotations in the docstring body, since those live
  in the function signature already).

## Markdown linting configuration

A couple of pymarkdown defaults are deliberately overridden:

- **`MD013` (line length)** — exempted for fenced code blocks, since
  reflowing code to fit a line-length limit isn't meaningful the way
  it is for prose. Fully disabled for `CHANGELOG.md` specifically,
  since it's regenerated by git-cliff on every release and can't
  reasonably be hand-wrapped.
- **`MD024` (duplicate headings)** — set to `siblings_only`, so
  repeated headings under *different* parent sections (e.g. `###
  Features` appearing under multiple `## [version]` headings in the
  changelog) aren't flagged as duplicates. Only true siblings under
  the same parent are still caught.

## Type checking

mypy runs in `strict` mode against the entire project, including any
future scripts and tooling outside `src/` and `tests/`. The package
ships a `py.typed` marker file (PEP 561) at
`src/swn_sector_generator/`, which tells mypy — and any consumer of
this package — that its type hints are complete and can be trusted
directly, rather than treating the package as untyped.

Run it manually with:

```bash
mypy .
```

## Commit message conventions

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/):

```text
type(scope): short description

optional body, one bullet per concern
```

Common types used in this project: `feat`, `fix`, `docs`, `style`,
`refactor`, `test`, `chore`, `build`, `ci`, `perf`, `revert`. Once
hooks are installed, gitlint enforces both the format and a 72
character title limit automatically — an invalid commit message will
be rejected before the commit is created.

## Changelog generation

Releases are documented via git-cliff, which generates
`CHANGELOG.md` from commit history grouped by type. To cut a new
release:

```bash
git cliff --tag vX.Y.Z -o CHANGELOG.md
git add CHANGELOG.md
git commit -m "docs(changelog): add vX.Y.Z release notes"
git tag -a vX.Y.Z -m "chore(release): vX.Y.Z"
git push origin main --tags
```

The version tag is created *after* the changelog commit, so it always
points to the commit containing its own release notes.

## Continuous integration

GitHub Actions runs on every push and pull request
(`.github/workflows/ci.yaml`), as two separate jobs:

- **Lint** — runs the same `.pre-commit-config.yaml` hooks used
  locally (ruff, mypy, yamllint, pymarkdown, generic file hygiene).
  Runs once, since lint results don't vary by OS.
- **Test** — runs the full pytest suite across a matrix of Linux,
  macOS, and Windows, since this project's cross-platform requirement
  means test *behavior* (unlike linting) genuinely can differ by
  platform.

Note that gitlint (commit-msg stage) and the pre-push pytest hook
don't run here — gitlint has no relevant event to attach to in CI,
and pytest is already covered by the dedicated Test job above.
